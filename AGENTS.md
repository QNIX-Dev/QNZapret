# AGENTS.md

## Назначение

Этот файл служит рабочим гайдом для агентов и участников разработки внутри `QNZapret`.
Он должен помогать быстро включаться в работу без повторного изучения текущего устройства проекта.

## Правило поддержки

`AGENTS.md` — это живой документ.
Его нужно обновлять всякий раз, когда проект меняется так, что это затрагивает архитектуру, платформенный охват, структуру папок, команды разработки, зависимости, стратегию интеграции или командные соглашения.
Если следующее изменение могло бы удивить нового агента, оно должно быть отражено здесь в рамках той же задачи или PR.

## Снимок проекта

- Проект: `QNZapret`
- Стек: Flutter + Dart
- Текущий тип приложения: кроссплатформенный frontend shell
- Поддерживаемые цели в репозитории сейчас: `android`, `linux`, `windows`
- Текущее состояние продукта: брендированный стартовый shell с заглушенным контрактом backend runtime
- Дизайн-направление: продуктовый интерфейс, а не стандартное демо Flutter

## Распределение ролей

- Над проектом работают как минимум два человека с разделением зон ответственности.
- Пользователь этого рабочего контекста отвечает преимущественно за backend-часть: runtime, нативные интеграции, bridge-слои, контракты, процессы, конфигурацию, статусы и логи.
- Второй участник проекта отвечает преимущественно за UI, UX и продуктовые экраны.
- Если задача сформулирована без дополнительных уточнений, агенту в этом контексте следует в первую очередь помогать именно с backend-направлением пользователя.
- Изменения в UI-слое без явной просьбы делать минимальными и только в той степени, в которой они нужны для backend-интеграции или работоспособности приложения.

## Текущая архитектура

### Точки входа

- `lib/main.dart`: минимальный bootstrap, вызывает `runApp`
- `lib/app/app.dart`: корневой `MaterialApp`

### Слой приложения

- `lib/app/theme/app_theme.dart`: общая визуальная система и типографика
- Тема намеренно оформлена как продуктовая и сейчас работает в dark-mode-first через `themeMode: ThemeMode.dark`

### Слой фич

- `lib/features/home/presentation/home_screen.dart`: текущий стартовый экран и UI-заглушка для runtime
- Этот экран уже показывает продуктовое направление, поддерживаемые платформы и ближайшие этапы

### Core/backend слой

- `lib/core/backend/proxy_runtime.dart`: общий контракт runtime
- Текущий backend-контракт включает:
  - `ProxyPlatform`
  - `ProxyRuntimeState`
  - `ProxyLaunchConfig`
  - `ProxyRuntimeSnapshot`
  - `ProxyRuntime`
  - `StubProxyRuntime`
- Будущие нативные интеграции должны развиваться от этого контракта, а не протаскивать платформенные детали напрямую в UI

## Рабочие соглашения

- В рамках задач пользователя по умолчанию приоритет у backend-логики, runtime-контрактов, интеграции с нативными компонентами, управления процессами, конфигурацией, статусами и логами.
- UI-часть может активно меняться вторым участником проекта, поэтому без явной необходимости не стоит вносить широкие визуальные или структурные правки в экранный слой.
- Если задача затрагивает и backend, и UI, сначала сохранять корректность интеграции и не ломать существующую работу второго участника по интерфейсу.
- Держать `main.dart` маленьким. Там должен жить bootstrap приложения, а не логика фич.
- Переиспользуемую общую настройку приложения размещать в `lib/app/`.
- Пользовательскую продуктовую функциональность размещать в `lib/features/<feature_name>/`.
- Общие runtime-контракты, адаптеры и абстракции платформенной интеграции размещать в `lib/core/backend/`.
- Не связывать UI напрямую с платформенным кодом, если сначала можно ввести общий интерфейс.
- Предпочитать расширение существующего runtime-контракта вместо разбрасывания backend-состояния по виджетам.
- Сохранять продуктовую визуальную подачу. Не откатывать экраны к generic template UI.
- Переиспользовать `AppTheme` и общие токены вместо того, чтобы разносить по проекту новые захардкоженные цвета и стили.

## Рекомендации по платформам

- Android — ожидаемая первая цель для реальной backend-интеграции.
- Linux и Windows по возможности должны следовать той же форме runtime-контракта.
- Платформенные адаптеры нужно держать за общим Dart API, чтобы UI работал с единой поверхностью runtime.
- Нативный bridge должен единообразно предоставлять запуск, остановку, статус и логи.

## Файлы, которые нужно трогать осторожно

- Избегать ручных правок сгенерированных Flutter-файлов, если только задача явно не требует регенерации.
- Особенно осторожно работать с файлами в:
  - `linux/flutter/`
  - `windows/flutter/`
  - сгенерированных платформенных build-артефактах
- Нативный код раннеров и манифесты, принадлежащие приложению, можно менять при необходимости, но generated registrant files обычно трогать не следует.

## Текущие продуктовые заметки

- Приложение является shell-оболочкой для будущего клиента с нативным Go backend.
- Пользователь ведет backend-направление, а UI и продуктовую подачу развивает второй участник проекта.
- Текущий UI намеренно подает QNZapret как реальный продукт, а не как прототип с экраном-счётчиком.
- Backend bridge сейчас заглушен и сообщает, что нативный Go runtime еще не подключен.
- В README упоминается `.sources/` как локальная зона для исследований и референсов, исключенная из Git; если этот процесс разовьется, его правила тоже нужно описать здесь.
